# 详细设计 · 核心数据结构

> 覆盖：判断卡片、前提假设跟踪表、洽谈问题、分析（研究）/框架、知识库实体、SQLite schema、贯穿主线机制。
> 这些结构是"红线原则"和"两轴工作法"的落地骨架——UI、导出、合规检查都由它们驱动。
>
> **术语**：「项目」＝待评估的业务合作/投资项目（deal）；「分析 / 研究」＝工作台对一个项目的一次评估（代码类型 `Analysis`）。"项目评估"维度仍指评估那个 deal。

---

## 1. 判断卡片 JudgmentCard（红线的核心载体）

框架 §0 要求：AI 每次下判断都要交出「立场 + 依据 + 把握度 + 哪条错了结论就翻」。这是**全局统一结构**，任何阶段的 AI 判断都用它。

```ts
interface JudgmentCard {
  id: string;
  scope: "项目" | "维度" | "可行性" | "风险项";   // 这张卡在评什么
  dimension?: DimensionKey;                        // 若挂在某维度
  stance: string;                                  // 立场/倾向（洽谈后可为 做|缓|弃）
  claim: string;                                   // 一句话主张
  grounds: Ground[];                               // 依据（可多条）
  confidence: "高" | "中" | "低";
  confidenceReason: string;                        // 把握度为什么是这档
  falsifiers: string[];                            // 哪几条前提错了，这个结论就翻
  openQuestions: string[];                         // 还没搞清、需继续追的
  status: "待审" | "已采纳" | "已推翻" | "已修订";  // 你审改后的状态
  history: RevisionNote[];                          // 你回灌新信息后它的重估轨迹
  createdAt: string; updatedAt: string;
}

interface Ground {
  point: string;                 // 论点
  evidence: string;              // 证据/数据
  source?: string;               // 来源（标口径）
  uncertainty?: string;          // 不确定性说明
}

interface RevisionNote {
  at: string;
  userInput: string;             // 你给的新信息/反驳
  aiAdjustment: string;          // AI 据此的重估
}
```

**UI 契约**：判断卡片必须渲染出全部四段（立场/依据/把握度/falsifiers），并带 `[反驳] [补充信息] [让它重估]` 三个动作。缺任一段 = 该输出不合格，前端标红提示重生成。

## 2. 前提假设 PremiseAssumption（贯穿主线的起点）

框架的贯穿主线：**前提假设 → 问题清单里最高优先几条 → 洽谈后逐条确认/推翻**。前提假设是这条线的锚。

```ts
interface PremiseAssumption {
  id: string;
  analysisId: string;
  text: string;                    // "这单成立"依赖的某个前提
  dimension: DimensionKey;         // 挂在哪个评估维度
  originStage: "调研前" | "洽谈中" | "洽谈后";
  isDealBreaker: boolean;          // 是否"错了就能推翻这单"→决定优先级
  status: "假设" | "待验证" | "已确认" | "已推翻" | "新出现";
  linkedQuestionIds: string[];     // 主线：转化成的问题
  resolution?: {                   // 洽谈后回填
    stage: string;
    verdict: "已确认" | "已推翻" | "仍待验证";
    evidence: string;              // 会议记录里的依据
  };
  createdAt: string; updatedAt: string;
}
```

- `isDealBreaker=true` 的假设 → 自动进洽谈问题清单的**最高优先级**。
- 洽谈后 AI 把会议记录**逐条映射**回这些假设，写 `resolution`，主线闭合。
- `status:"新出现"` 专门装"本次洽谈冒出、原框架未覆盖"的信息 → 可回灌 Step 0 改框。

## 3. 洽谈问题 Question（维度产出的是问题，不是分数）

```ts
interface Question {
  id: string;
  analysisId: string;
  dimension: DimensionKey;
  text: string;                    // 具体问题
  intent: "要查什么" | "要问对方什么" | "还没搞清什么";
  fromAssumptionId?: string;       // 若由前提假设转化而来
  priority: number;                // deal-breaker 假设来的排最前
  answered?: { at: string; note: string };
}
```

> UI 硬约束：洽谈/评估阶段**只渲染问题，不渲染任何评分/星级**（框架 §6，评分留到洽谈后信息足够时）。

## 4. 分析（研究）与框架（活草稿）

```ts
type DimensionKey =
  | "行业理解" | "对方画像" | "项目评估"
  | "风险维度" | "战略布局匹配" | "我方角色";   // 通用核心 6 维

interface Analysis {
  id: string; name: string;
  ourRole: string;                 // Step 0 先确认：资金方/场地方/货源方/运营方/牵头整合/客户...
  industry: string;
  framework: Framework;            // 本单的评估框架（活草稿）
  createdAt: string; updatedAt: string;
}

interface Framework {              // 框架是"活草稿"，可随分析改
  coreDimensions: {                // 核心层全量启用，按角色排权重
    key: DimensionKey;
    weight: number;                // 由我方角色决定
    weightReason: string;
  }[];
  industryOverlay: {               // 行业叠加层：由 Step 0 当场产出
    item: string;                  // 该行业特有监管/牌照/交易惯例/特有问题
    reason: string;
  }[];
  reflexiveNotes: string[];        // AI 反问"这框架可能漏了什么"及你的回应
}
```

- **核心层 6 维全量启用、不做取舍**；变量在"叠加层里装什么"。
- 角色不同 → 各维度权重不同（`weight` + `weightReason`）。

## 5. 交付物与耐用度分级

框架 §5 把交付物分半耐用/易耗。数据层据此分区存储与复用。

| 交付物 | 耐用度 | 存储 |
|---|---|---|
| 行业深度分析 | 半耐用 | **知识库**（跨项目、版本化） |
| 企业画像 | 半耐用 | **知识库**（同一家再来可复用） |
| 洽谈问题清单 | 易耗 | 项目内，一单一弃 |
| 合作备忘（可行性 + 交易结构图） | 易耗 | 项目内归档 |

### 知识库实体（复利资产）

```ts
interface IndustryAnalysis {        // 半耐用
  id: string; industry: string; version: number;
  roleLens: string;                 // 角色视角（第 6 条验收线）
  backbone: string;                 // 决策主心骨（第 1 条）
  stratificationAxis: string;       // 劈开行业的分层轴（第 2 条）
  quantRanges: { metric: string; range: string; source: string; uncertainty: string }[]; // 第 3 条：量化+口径
  keyVariables: string[];           // 命门变量（第 4 条）
  namedRisks: { risk: string; regRedline?: string; caseRef?: string }[];      // 第 5 条：有名有姓
  premiseAssumptions: string[];     // 产出"这单成立的前提假设"
  updatedAt: string;
}

interface EnterpriseProfile {       // 半耐用
  id: string; company: string; version: number;
  demands: string;                  // 真实诉求/动机
  capabilities: { finance?: string; credit?: string; delivery?: string; track?: string };
  decisionChain: { name: string; role: string; note?: string }[];  // 决策链关键人
  alternatives: string;             // 替代选项 = 我方筹码
  updatedAt: string;
}
```

复用规则：新建分析选行业/企业时，命中已有条目 → 提示"可复用/需更新"；更新产生新 `version`，旧版本留痕。

## 6. SQLite Schema（草案）

```sql
-- 项目区（易耗为主）
CREATE TABLE analyses(id TEXT PRIMARY KEY, name TEXT, our_role TEXT, industry TEXT, created_at TEXT, updated_at TEXT);
CREATE TABLE frameworks(analysis_id TEXT, json TEXT);            -- Framework 序列化
CREATE TABLE assumptions(id TEXT PRIMARY KEY, analysis_id TEXT, json TEXT);
CREATE TABLE questions(id TEXT PRIMARY KEY, analysis_id TEXT, json TEXT);
CREATE TABLE judgment_cards(id TEXT PRIMARY KEY, analysis_id TEXT, json TEXT);
CREATE TABLE meetings(id TEXT PRIMARY KEY, analysis_id TEXT, transcript_path TEXT, created_at TEXT);
CREATE TABLE deliverables(id TEXT PRIMARY KEY, analysis_id TEXT, kind TEXT, path TEXT, created_at TEXT);

-- 知识库区（半耐用、跨项目、版本化）
CREATE TABLE industry_analyses(id TEXT PRIMARY KEY, industry TEXT, version INTEGER, json TEXT, updated_at TEXT);
CREATE TABLE enterprise_profiles(id TEXT PRIMARY KEY, company TEXT, version INTEGER, json TEXT, updated_at TEXT);
```

- 长文（行业分析正文、会议记录、导出物）落**本地文件**，表里存路径；结构化字段进 JSON 列，便于检索与 UI 驱动。
- 知识库与项目区物理分离——半耐用资产不随某个项目删除而丢失。

## 7. 贯穿主线机制（把三张表连起来）

```
PremiseAssumption(isDealBreaker) ──生成──▶ Question(priority 最高)
        ▲                                          │
        │  洽谈后 resolution 回填                     │ 洽谈中带着问题去问/去查
        └──────── 会议记录映射 ◀──── Meeting transcript ┘
```

- **调研前**：行业分析/企业画像产出 `PremiseAssumption`。
- **洽谈中**：`isDealBreaker` 的假设自动转 `Question` 并置顶。
- **洽谈后**：AI 把会议记录逐条映射回假设，写 `resolution`（已确认/已推翻/仍待验证/新出现），主线闭合，并生成可行性 `JudgmentCard`。
- UI 顶部时间线直接由这条链渲染，随时可见"哪些能推翻这单的假设，现在验到哪了"。
